High-performance computing has always run on bare metal, as close to the
processor as possible. But Kubernetes is spreading into HPC for its
portability and orchestration, so the question is no longer "can we run MPI
on Kubernetes?" but "what does that flexibility cost?" We measured it.

## The setup

Same machine for both, to keep it fair: earth04, a node of Universitas
Padjadjaran's Guriang HPC facility, with 64 cores and 128 GB of RAM.

## What we found

We expected Kubernetes to cost performance. At the top of the range, it
didn't: at 32 cores Kubernetes ran 45.7 timesteps per second, 8.8% ahead of
bare metal, with less network overhead and less of the CPU spent on
communication. Averaged across 2 to 32 cores, the picture is closer, with an
average slowdown of 7.6%.

The OSU benchmark showed bandwidth peaking at 32 KB and 64 KB messages, the
same shape reported in earlier research on HPC over Kubernetes (Beltre et
al., 2019).

## Why it might be faster

Our best guess, and only a guess: Kubernetes puts every worker in its own
Linux control group, which may let each one use the L1 and L2 caches more
effectively. On bare metal, the OS scheduler treats MPI ranks like any other
process.

## The catch

This ran on a single node. Every message between pods crossed a virtual
bridge in the kernel, never a physical network. Real Kubernetes clusters
span many nodes, where traffic picks up physical latency and the overhead of
the container network. The result needs testing on a multi-node cluster
before anyone migrates on the strength of it.
